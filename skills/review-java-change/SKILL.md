# 审查 Java 改动

## 何时使用

用户要求审查代码、PR、本地 diff、或「看看这样改有没有问题」时使用。

## 审查流程

1. 明确变更范围（模块、接口、表结构）
2. 对照 `.cursor/rules` 与同目录既有实现
3. 按下方清单输出结论；问题必须带**文件路径 + 原因 + 建议改法**

## 清单

### 正确性与边界

- [ ] 空值、幂等、并发（库存/余额等）是否考虑
- [ ] 事务边界是否合理（`@Transactional` 位置、异常回滚类型）
- [ ] 与调用方契约（DTO 字段、错误码、分页结构）是否破坏兼容

### 分层与风格

- [ ] Controller 是否过厚；是否正确使用 `Result`/`ApiController`
- [ ] 是否绕过 Service 直操 Mapper
- [ ] 命名与同模块一致（Add/Update/Query DTO）

### 安全

- [ ] 是否缺少鉴权/权限注解（对照同类接口）
- [ ] SQL 注入风险（拼接 SQL、`${}` 滥用）
- [ ] 敏感信息是否进日志或响应

### 数据与性能

- [ ] 新索引/SQL 是否匹配真实查询；有无 N+1、全表扫隐患
- [ ] 缓存与 DB 一致性（若涉及 Redis）
- [ ] 大对象、无界列表是否限制分页

### 工程

- [ ] 是否最小改动；有无无关重构
- [ ] 依赖版本是否走父 POM
- [ ] demo 代码是否误入库为生产依赖

## 输出格式

```markdown
## 结论
（通过 / 有条件通过 / 不通过）— 一句话

## 必须修改
- `path`: 问题 → 建议

## 建议改进
- ...

## 可后续处理
- ...
```

严重问题（安全、资损、数据损坏）标为**必须修改**；风格问题放建议。
